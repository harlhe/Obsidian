![[Pasted image 20250828170229.png]]1. **`[*] --> Disconnected` (断开连接)**
    
    - `[*]`: 代表流程的起点。
        
    - `Disconnected`: 这是系统的**初始和最终稳定状态**。表示当前没有任何活动的网络连接。
        
2. **`Disconnected --> Connecting: connect()` (正在连接)**
    
    - 当外部调用 `connect()` 函数时，状态从 `Disconnected` 切换到 `Connecting`。
        
    - `Connecting` 是一个过渡状态，代表客户端正在尝试建立底层的网络传输通道（例如，创建一个WebSocket或TCP连接）。
        
3. **`Connecting --> Initializing: transport ready` (初始化中)**
    
    - 当底层的网络通道（transport）成功建立后，状态切换到 `Initializing`。
        
    - `Initializing` 也是一个过渡状态。在这个阶段，客户端和服务器已经“接通电话”，但还没有开始正式交谈。它们需要进行一次“握手”。
        
4. **`Initializing --> Ready: capabilities exchanged` (准备就绪)**
    
    - **这是与我们之前讨论的MCP协议最关键的连接点**。在初始化阶段，客户端和服务器会交换各自的**能力 (`capabilities`)**。这就是 `McpCapabilities` 接口发挥作用的地方。
        
    - 当双方成功完成能力协商，互相了解了对方的功能后，连接才真正准备好进行业务通信，状态切换到 `Ready`。
        
    - `Ready` 是系统的**主要工作状态**。
        

#### 工作状态

- **`Ready --> Ready: request/response`** 和 **`Ready --> Ready: notification`**
    
    - 一旦进入 `Ready` 状态，客户端就可以开始发送JSON-RPC的**请求/响应**消息和**通知**消息。
        
    - 这些操作是循环的，并不会改变 `Ready` 状态，表明连接正处于活跃和健康的工作阶段。
        

#### 正常关闭流程

1. **`Ready --> Closing: close()` (正在关闭)**
    
    - 当外部调用 `close()` 函数时，表示希望进行一次**优雅的关闭**。
        
    - 状态切换到 `Closing`，开始执行关闭连接的清理工作（例如，发送断开连接的信令）。
        
2. **`Closing --> Disconnected: closed` (断开连接)**
    
    - 当所有清理工作完成，连接被完全释放后，状态回归到初始的 `Disconnected` 状态，完成一个完整的生命周期。
        

#### 异常处理流程

1. **`Connecting --> Failed: error` (失败)**
    
    - 如果在 `Connecting` 阶段发生错误（例如，网络不通、服务器地址错误、DNS解析失败），状态会切换到 `Failed`。
        
2. **`Initializing --> Failed: negotiation failed` (失败)**
    
    - 如果在 `Initializing` 阶段发生错误（例如，能力协商失败、协议版本不匹配、认证失败），状态同样会切换到 `Failed`。
        
3. **`Failed --> Disconnected: reset` (断开连接)**
    
    - 进入 `Failed` 状态后，系统可以通过 `reset` 操作（例如，在尝试几次重连失败后）将状态重置回 `Disconnected`，以便之后可以重新发起连接。

// Bidirectional streaming payload structures
interface BidirectionalStreamingProtocol {
  // Client → Server
  clientPayload: {
    bytes: string  // Base64 encoded
    encoding: 'base64'

    // Decoded content types
    contentTypes:
      | ContinuedUserInput
      | ToolResultBlock
      | ConversationTurnInput
  }

  // Server → Client
  serverPayload: {
    bytes: string  // Base64 encoded
    encoding: 'base64'

    // Decoded event types
    eventTypes:
      | ContentBlockDeltaEvent
      | ToolUseRequestEvent
      | ErrorEvent
      | MetadataEvent
  }
}

// The streaming state machine for bidirectional flows
class BidirectionalStreamManager {
  private encoder = new TextEncoder();
  private decoder = new TextDecoder();
  private buffer = new Uint8Array(65536);  // 64KB buffer

  async *processStream(stream: ReadableStream) {
    const reader = stream.getReader();
    let partial = '';

    while (true) {
      const { done, value } = await reader.read();
      if (done) break;

      // Decode and split by newlines (SSE format)
      partial += this.decoder.decode(value, { stream: true });
      const lines = partial.split('\\n');
      partial = lines.pop() || '';

      for (const line of lines) {
        if (line.startsWith('data: ')) {
          const payload = JSON.parse(line.slice(6));
          yield this.decodePayload(payload);
        }
      }
    }
  }

  private decodePayload(payload: any) {
    const bytes = Buffer.from(payload.bytes, 'base64');
    // Further decode based on protocol buffers or JSON
    return JSON.parse(bytes.toString());
  }
}

### `BidirectionalStreamingProtocol` 接口详解

这个接口是整个通信系统的**“协议契约”**。它严格定义了在双向流中，客户端和服务端各自可以发送什么类型的消息。

一个有趣的设计是，无论哪个方向的负载，都采用了**“双层封装”**的模式：最外层是一个包含 `bytes` 字段的JSON，而 `bytes` 字段本身是一个 **Base64 编码**的字符串，真正的业务数据被编码在这里面。这种设计的好处是**灵活性**：外层协议保持简单统一，而内层的数据可以是更复杂的格式，比如另一个JSON，甚至是二进制的Protobuf。

#### `clientPayload`: 客户端 → 服务器

定义了客户端在连接建立后，可以主动发送给服务器的消息类型。

- `ContinuedUserInput`: **连续的用户输入**。这表明用户的一个长输入可能会被拆分成多个数据块流式发送给服务器，可能用于实现实时预览、自动补全或即时验证等高级功能。
    
- `ToolResultBlock`: **工具结果块**。我们很熟悉这个，当客户端执行完工具后，通过这个类型将结果发送回服务器。
    
- `ConversationTurnInput`: **会话轮次输入**。这代表一次完整的、标准的用户输入。
    

#### `serverPayload`: 服务器 → 客户端

定义了服务器可以主动推送给客户端的事件类型。

- `ContentBlockDeltaEvent`: **内容块增量事件**。这就是我们熟悉的 `ContentBlockDelta`，用于实现“打字机效果”的文本流。
    
- `ToolUseRequestEvent`: **工具使用请求事件**。当LLM决定使用工具时，服务器通过这个事件将 `ToolUseBlock` 推送给客户端。
    
- `ErrorEvent`: **错误事件**。用于向客户端发送结构化的错误信息。
    
- `MetadataEvent`: **元数据事件**。用于发送额外的信息，例如在一次完整的LLM响应结束后，发送包含 `TokenUsage` 的元数据。

### `BidirectionalStreamManager` 类详解

这个类是**客户端的“流处理器”**。它的核心职责是接收来自服务器的原始字节流 (`ReadableStream`)，并将其解码、解析成一个个有意义的、可供上层应用使用的事件对象。

#### 核心属性

- `encoder`, `decoder`:标准的文本编/解码器，用于字符串和字节数组(`Uint8Array`)之间的转换。
    
- `buffer`: 一个预分配的缓冲区，用于提高处理性能。
    

#### `async *processStream` 方法

这是这个类的核心。`async *` 语法定义了一个**异步生成器 (Async Generator)**，这是一种处理流式数据的完美模式。这意味着调用这个函数的代码可以通过 `for await...of` 循环来消费它 `yield` (产出) 的一个个处理好的事件。

**工作流程分解:**

1. **读取原始数据块**: `while (true)` 循环通过 `reader.read()` 不断从网络流中读取原始的字节数据块 (`value`)。
    
2. **解码、缓冲与分行**:
    
    - `partial += this.decoder.decode(value, { stream: true });`: 将字节解码成字符串，并追加到 `partial` 缓冲中。`{ stream: true }` 选项可以正确处理跨数据块的UTF-8字符。
        
    - `const lines = partial.split('\\n');`: 按换行符 `\n` 切分字符串。这是因为底层的传输格式**采用了类似SSE的、用换行符分隔消息的模式**。
        
    - `partial = lines.pop() || '';`: 将数组的最后一个元素（它可能是一个不完整的行）重新赋值给 `partial`，留待与下一个数据块拼接。
        
3. **解析SSE格式并产出**:
    
    - `for (const line of lines)`: 遍历所有已接收到的完整行。
        
    - `if (line.startsWith('data: '))`: 检查该行是否符合SSE的 `data:` 前缀格式。
        
    - `const payload = JSON.parse(line.slice(6));`: 移除前缀，并将剩余的JSON字符串解析成外层对象（即 `serverPayload`）。
        
    - `yield this.decodePayload(payload);`: 调用 `decodePayload` 方法进行“内层”解码，然后通过 `yield` 将最终的、完全解码的事件对象**“产出”**给外部的调用者。
        

#### `decodePayload` 方法

这个私有方法负责处理**第二层解码**。

1. `const bytes = Buffer.from(payload.bytes, 'base64');`: 从外层对象中取出 `bytes` 字段，并进行Base64解码，得到原始的内部负载字节。
    
2. `return JSON.parse(bytes.toString());`: 这个示例的实现假设内部负载也是JSON。它将解码后的字节转换成字符串，然后再进行一次JSON解析，得到最终的 `ContentBlockDeltaEvent` 或 `ToolUseRequestEvent` 等事件对象。
    

### 总结

这套代码描绘了一个强大而灵活的自定义双向流协议。

- **协议层面**，它通过“JSON -> Base64 -> 内部负载”的双层封装，兼顾了协议的结构性和内容的灵活性。
    
- **处理层面**，`BidirectionalStreamManager` 使用高效的异步生成器模式，清晰地分离了“网络IO”、“协议解析（SSE）”和“负载解码（Base64）”这几个步骤。
    

这套架构使得客户端和服务器之间可以进行非常丰富的实时交互，例如，客户端可以在向服务器流式传输工具结果的同时，接收来自服务器的新的文本内容流，为构建高度动态和响应迅速的AI应用提供了坚实的基础。
