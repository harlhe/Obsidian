# AI 自动化测试技术范式与方案选型

## 概述

本文档基于当前 AI 自动化测试项目的全部材料，系统分析测试技术范式的演变、现有方案对比以及选型建议，为技术决策提供依据。

## 技术范式演变

### 从脚本驱动到意图驱动

#### 传统模式特征
- 人工编写脚本
- 显式指定定位器、等待逻辑、断言方式
- 出错后回到代码层修脚本
- 强依赖定位器和稳定页面结构
- 强依赖人工处理环境与依赖

#### 新模式特征
- 人工给出目标
- 模型自己规划路径
- 工具负责执行动作
- 模型根据结果继续迭代
- 可以直接从目标描述出发
- 可以把页面当作视觉对象而不只是 DOM 树
- 可以把失败当作中间状态而不是终止状态
- 可以在多种工具与多条策略之间切换

### 核心技术能力组合

完整的技术体系由以下能力组合而成：

1. **大模型作为"大脑"**
   - 理解自然语言测试目标
   - 拆解执行步骤
   - 判断当前执行结果是否符合预期
   - 在失败后重新规划下一步
   - 整理测试过程并输出报告

2. **Agent 框架作为执行编排层**
   - 接收自然语言意图
   - 调度 Agent 执行具体任务
   - 把模型推理结果映射成对环境的操作
   - 支持多 Agent 协作
   - 给失败重试、反馈修正、持续执行提供运行框架

3. **MCP / Playwright 作为浏览器执行层**
   - 启动浏览器、打开页面
   - 输入查询、点击链接和菜单
   - 等待页面加载、截图
   - 获取页面上下文

4. **Vision / OCR 作为视觉断言层**
   - 看懂页面布局
   - 在图片流中识别目标封面
   - 判断多个版本封面是否存在
   - 识别封面上的文字
   - 对截图结果进行验证

5. **环境修复与依赖安装作为自愈层**
   - 检查并自动安装依赖
   - 发现并修正环境问题
   - 在方案失败后自动切换备选方案

### 核心闭环机制

完整的测试执行闭环：
- **目标**：用户用自然语言给出测试目标与验收条件
- **执行**：Agent 框架把步骤分发给工具层执行
- **观察**：感知层采集页面截图、DOM 摘要、控制台错误等
- **判断**：模型根据执行结果决定继续、修正、重试或换方案
- **纠错**：智能回退层在执行失败时不立即中断，尝试自动修复
- **输出**：报告层把执行结果变成可信交付

## 方案对比分析

### 五类候选方案

#### 方案 A：传统 Playwright / Selenium 脚本自动化

**核心做法**
- 直接写 TS / JS / Python 脚本
- 显式管理定位器、等待逻辑、断言和环境依赖
- 在 CI 或本地执行

**优点**
- 可控性高
- 调试手段成熟
- 与现有工程体系兼容
- 结果相对稳定

**缺点**
- 页面一改脚本就要维护
- 添加新场景成本高
- 很难覆盖图片识别、模糊对象查找、多软件协同
- 对 PM / 业务人员不友好

**适合场景**
- 核心稳定流程
- 回归烟测
- 需要高确定性的固定动作

#### 方案 B：纯 AI 浏览器代理

**核心做法**
- 直接给模型一个自然语言任务
- 由 AI 自主决定点击、输入、滚动、跳转和验证
- 典型代表是 `browser-use` 的 prompt 模式

**优点**
- 上手快
- 对非工程人员更友好
- 对页面变化的适应性可能更强
- 容易覆盖探索式和视觉型任务

**缺点**
- 过程不可控时，团队会缺乏信任
- token 成本高
- 稳定性受模型表现波动影响大
- 同一任务多次执行可能路径不同

**适合场景**
- 快速验证
- 探索式测试
- 页面结构变化频繁的阶段

#### 方案 C：Browser-use / Agent Browser + 固定场景脚本

**核心做法**
- 底层仍是浏览器代理能力
- 上层把测试场景固化成脚本或配置

**优点**
- 比纯 prompt 更可复用
- 可以沉淀固定场景
- 已经能做一键执行、报告输出
- 便于快速搭出最小闭环

**缺点**
- 如果场景固化得太死，灵活性会下降
- 如果脚本层过厚，又会回到传统脚本维护痛点
- 文档和环境门槛容易压垮推广

**适合场景**
- 团队内部第一阶段验证
- 已知关键路径场景
- 需要"先跑起来"的阶段

#### 方案 D：MCP / IDE 集成式 AI 测试

**核心做法**
- 通过 MCP 把测试能力接入 Claude、Cursor、IDE 或开发工具
- 测试更靠近开发流，而不是单独平台

**优点**
- 更贴近开发者工作流
- 适合开发阶段即时验证
- 可与代码修改、日志、截图联合使用
- 可自然接入"改代码 -> 跑测试 -> 看报告"的闭环

**缺点**
- 更依赖 IDE 生态
- 非开发角色使用门槛仍然偏高
- 工程实现通常比简单脚本更复杂

**适合场景**
- 前端开发自测
- AI 编程协同
- 本地开发闭环

#### 方案 E：一体化 AI 测试平台

**核心做法**
- 提供场景管理、调度、历史、告警、报告、权限等完整平台能力

**优点**
- 适合团队协作和持续运营
- 资产沉淀完整
- 平台视角更强
- 后期更容易扩展到组织级

**缺点**
- 研发成本高
- 平台先行容易过重
- 如果底层执行稳定性不足，平台价值会被拖垮

**适合场景**
- 中后期产品化
- 多团队共享
- 需要调度、历史和可观测性的场景

### 方案横向对比

| 方案 | 自然语言友好度 | 稳定性 | 维护成本 | 可见性 | 新场景扩展 | 多软件协同 | 成本 | 当前建议 |
|------|---------------|--------|----------|--------|------------|------------|------|----------|
| A. 传统脚本 | 低 | 高 | 高 | 高 | 中 | 低 | 低到中 | 保留为基础能力 |
| B. 纯 AI 代理 | 高 | 低到中 | 低 | 低到中 | 高 | 中到高 | 高 | 不建议直接作为主路线 |
| C. AI 代理 + 固定场景 | 中到高 | 中 | 中 | 中到高 | 中 | 中 | 中到高 | 最适合当前阶段 |
| D. MCP / IDE 集成 | 中 | 中 | 中 | 高 | 高 | 中 | 中到高 | 适合作为第二阶段增强 |
| E. 一体化平台 | 中 | 取决于底层 | 中到高 | 高 | 高 | 中 | 高 | 不建议先做 |

## 行业技术生态

### 行业常见方案分类

| 类型 | 代表方案 | 核心思路 | 更适合什么场景 |
|------|----------|----------|----------------|
| 代码生成型 E2E | QA Wolf、KaneAI、mabl、Functionize、Testim | AI 帮生成/维护测试代码或测试步骤，最终还是落到 Playwright / Appium / 平台资产 | CI 回归、团队协作、稳定执行 |
| 自然语言浏览器框架 | Stagehand、Momentic | 自然语言驱动浏览器，强调 self-healing、低门槛和可维护性 | 想快速起量，但不想完全黑盒 |
| 视觉型 computer-use | browser-use、OpenAI Computer Use | 看截图、点、输、滚，像人一样操作页面 | 探索式测试、复杂跨站流程、真实业务链路 |
| Playwright / DOM Agent 型 | Playwright Agents、Playwright Locators | 基于 DOM / locator / role 做更确定的测试执行和 agent 辅助 | 工程化自动化、IDE 调试、稳定资产 |
| 通用 agent runtime | OpenClaw、Browserbase MCP 等 | 把浏览器、shell、网页读取统一成 agent runtime | 平台化、统一入口、服务化共享 |
| 视觉验证平台 | Applitools | 用视觉 AI 做 UI 对比、视觉回归、界面一致性验证 | 视觉回归、跨浏览器 UI 检查 |

### 技术发展趋势

1. **从工具到服务化**：AI Agent 从个人本地工具推进到可浏览器访问、可远程使用、可组织级部署的服务能力
2. **交互壳和 AI 内核分离**：同一个内核可以有 CLI、Web、IDE 等多种入口
3. **团队共享能力的产品方向**：当 AI 工具从"我自己用"变成"团队共同访问"，开始进入平台化和治理问题

## 当前项目方案

### 双轨制方案

基于实践验证，当前项目采用双轨制方案：

#### 路线一：testAgent + browser-use

**方案定位**
- 面向 DevStar 的 AI 自动化测试运行时
- 把自然语言测试、固定测试、真实浏览器执行、本地环境准备、测试报告统一到一个测试内核

**核心价值**
- 能直接跑真实业务流：登录、建仓、提 PR、开 IDE
- 适合探索式测试和临时验收
- 适合产品演示、现场验证、客户环境验证
- 适合页面刚改完、还没沉淀稳定脚本的时候

**当前成果**
- DevStar 23 个核心场景主链路已基本跑通
- 支持自然语言描述测试目标
- 生成详细的测试报告和证据

#### 路线二：OpenClaw + coding-agent skill + Playwright

**方案定位**
- 让 OpenClaw / coding-agent 帮助生成、维护和组织 Playwright 测试资产
- 最终由 Playwright 做确定性执行

**核心价值**
- 更标准化
- 更容易接 CI
- 更适合代码评审、版本管理、长期维护
- 更适合把已验证通过的场景沉淀成长期回归资产

**当前成果**
- 已验证 AI 生成 Playwright 资产路线可行
- 已生成 23 个 DevStar 场景对应的 Playwright spec
- 代表场景已确认 PASS

### 两条路线关系

**不是二选一，而是组合使用**
- 先用 `testAgent + browser-use` 把场景跑通
- 再用 `OpenClaw + Playwright` 把稳定场景沉淀成标准测试资产

| 维度 | `testAgent + browser-use` | `OpenClaw + coding-agent + Playwright` |
|------|---------------------------|----------------------------------------|
| 核心优势 | 灵活、泛化强、能跑复杂真实流程 | 稳定、可维护、适合回归和 CI |
| 适合阶段 | 场景探索、临时验证、真实业务验收 | 场景固化、持续回归、团队协作 |
| 最佳角色 | AI 测试执行器 | AI 测试资产生成器 |

## 选型建议

### 当前阶段推荐：方案 C + D 的组合

**建议主线采用**
- 本地一键脚本作为入口
- 场景文件作为资产形态
- 浏览器最小执行器作为稳定基座
- AI 作为截图理解、异常回退、报告生成层
- 预留 MCP 接口，后续接入 IDE / Claude / Cursor

**这条路线的好处**
- 能快速交付
- 能被开发和测试人员使用
- 不会马上掉进纯平台化的大坑
- 保留未来产品化空间

### 不建议当前阶段主推的路线

1. **不建议只做传统脚本**
   - 原因是会重新回到维护成本问题

2. **不建议只做纯 AI prompt 测试**
   - 原因是稳定性、可见性和成本都不够可控

3. **不建议现在就先做重平台**
   - 原因是底层执行与场景资产尚未收敛，平台化会放大混乱

### 阶段性选型策略

#### 短期
**主推 `testAgent + browser-use`**
- 先把核心业务链路跑通
- 先验证哪些场景值得做自动化
- 先解决探索式测试和现场验收问题

#### 中期
**把高频稳定场景逐步转成 `OpenClaw + Playwright` 资产**
- 登录
- 建仓
- PR 创建
- DevContainer
- Workflow
- MCP / IDE 可见性

#### 长期
**形成"双轨制测试体系"**
1. AI 运行时测试 - 负责探索、验收、复杂真实链路
2. 标准 Playwright 回归测试 - 负责稳定回归、CI、团队协作

## 关键判断

### 判断 1：团队不适合走"纯 AI 黑盒"主路线

会议纪要中反复出现的问题都是：
- 过程要看得见
- 结果不能只看 pass / fail
- 安装和执行路径要清楚

这和纯黑盒代理天然冲突。因此，纯 AI 更适合作为能力层，而不是直接作为最终产品形态。

### 判断 2：团队当前最优路线是"混合型方案"

最佳平衡点不是传统脚本，也不是纯 prompt，而是：
- 场景文件负责复用和版本化
- 最小执行器负责稳定动作
- AI 负责规划、视觉判断、异常回退和报告整理

这正好吻合需求中"像脚本一样读取文件执行"和"用自然语言控制验证"的双重诉求。

### 判断 3：先单机跑通，再平台化

当前真正卡住的不是平台能力，而是：
- 安装复杂
- 文档不清
- 新场景添加不够简单
- 方案细节认知没有完全对齐

所以现阶段重点不应该是 K8S、大规模调度、组织级平台，而是：
- 一键安装
- 一键运行
- 六个典型场景稳定跑通
- 报告足够可信

### 判断 4：报告能力不是附属功能，而是核心产品价值

团队多次强调"测试的核心是发现问题"，这意味着报告必须包含：
- 执行步骤
- 截图 / 证据
- 失败原因
- 期望与实际差异
- 问题优先级或问题分类

如果只有 `pass/fail`，那这条产品线很难建立信任。

## 结论

基于当前文件夹里的全部材料，团队最适合的路线不是某个现成开源项目的直接照搬，而是采用"AI 编排 + 最小执行器 + 文件化场景 + 可见报告"的混合方案。

对比所有候选路径后，可以得出一个清晰结论：
- 传统脚本适合作为底座，但不应继续做成主交互方式
- `browser-use` 一类项目提供了重要方向，但更适合作为能力参考而不是完整答案
- 团队当前最值得做的，是把本地一键、场景复用、过程可见和报告可信四件事先做扎实
