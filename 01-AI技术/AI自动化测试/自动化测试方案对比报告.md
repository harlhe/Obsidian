# 自动化测试方案对比报告

## 报告目的

基于 `AI自动化测试` 文件夹内的全部材料，梳理当前团队在前端 / AI 自动化测试方向上讨论过的方案，给出横向对比、阶段判断和推荐路线。

## 资料范围

本报告综合了以下 5 份文件：

- `需求.md`
- `3.11会议纪要.md`
- `3.18会议纪要.md`
- `前端 AI 自动化测试：brower-use 调研.md`
- `小龙虾总结.md`

## 材料摘要

### 1. `需求.md`

只有三句话，但信息非常集中：

- 目标不是写脚本，而是“用自然语言控制功能操作并验证结果”。
- 方案方向不是预设死的，明确提到了 agent-browser 一类路线。
- 仍然希望保留“像脚本一样读取文件自动化执行”的能力。

这决定了最终方案不能只有纯 prompt，也不能只有传统脚本，必须兼顾自然语言入口和文件化复用。

### 2. `3.11会议纪要.md`

这份纪要更像第一次方案校准，释放了几个关键信号：

- 团队对纯 AI 黑盒测试不放心，担心“无法感知过程”。
- 测试目标被强调为“发现问题”，而不只是“跑通并通过”。
- 团队已经意识到传统 Playwright 脚本维护成本高、页面一变脚本就碎。
- 当时已出现“AI 编排 + 自研执行器”的方向。
- 更偏向单机先验证，而不是直接上 CI / 分布式平台。
- 孟宁希望的是“能直接控制桌面、多软件协同、通过提示词重复执行”的框架。

### 3. `3.18会议纪要.md`

这份纪要体现的是一周后的收敛：

- 已经做出一键脚本，说明方向从讨论进入了工程验证。
- 当前实现基于 agent browser / skill 编排浏览器动作，已有固定场景。
- 有 `pass/fail` 和详细报告输出，说明报告体系已经被纳入核心交付。
- 使用截图反馈给 AI 决策，意味着视觉闭环已经进入方案核心。
- 主要痛点转成了安装复杂、文档不足、新场景扩展不够简单。
- 团队开始明确要求“行业对比”和“从安装到交互的全流程评估”。

### 4. `前端 AI 自动化测试：brower-use 调研.md`

这份是外部路线调研，价值在于把候选生态补齐了：

- `browser-use`：自然语言驱动浏览器操作的基础能力层。
- `vibetest-use`：MCP 方式接入 Claude / Cursor，一种 IDE 协同测试模式。
- `qa-use`：一体化平台，带用例管理、调度、历史追踪和通知。
- `SDET-GENIE`：从用户故事生成手工 case，再派生自动化代码。
- `web-eval-agent`：更偏开发过程提效，重视可视化监控和 UX 报告。

同时它也明确了两个现实问题：

- token 成本会很快成为瓶颈。
- 本地模型虽然便宜，但效果和速度明显不够。

### 5. `小龙虾总结.md`

这份总结把技术范式讲得最清楚：

- 测试正在从脚本驱动走向目标驱动。
- 关键能力组合是：大模型 + Agent 编排 + MCP / Playwright + Vision + OCR + 环境自愈。
- 最大变化不在“能写代码”，而在“能围绕目标持续行动、纠错、切换方案并输出报告”。

## 统一问题定义

把五份材料放在一起，团队真正想解决的问题可以归纳成 6 个：

1. 让测试入口从“写脚本”降低为“写自然语言或场景文件”。
2. 降低传统端到端脚本的维护成本。
3. 保留可重复执行、可版本化、可 review 的资产形态。
4. 让执行过程可见，不接受纯黑盒结果。
5. 输出面向问题发现的结构化报告，而不是只有通过率。
6. 先在本地一键跑通，再考虑更重的平台化能力。

## 候选方案

为便于决策，这里把现有讨论收敛成 5 类路线。

### 方案 A：传统 Playwright / Selenium 脚本自动化

核心做法：

- 直接写 TS / JS / Python 脚本。
- 显式管理定位器、等待逻辑、断言和环境依赖。
- 在 CI 或本地执行。

优点：

- 可控性高。
- 调试手段成熟。
- 与现有工程体系兼容。
- 结果相对稳定。

缺点：

- 页面一改脚本就要维护。
- 添加新场景成本高。
- 很难覆盖图片识别、模糊对象查找、多软件协同。
- 对 PM / 业务人员不友好。

适合：

- 核心稳定流程。
- 回归烟测。
- 需要高确定性的固定动作。

### 方案 B：纯 AI 浏览器代理

核心做法：

- 直接给模型一个自然语言任务。
- 由 AI 自主决定点击、输入、滚动、跳转和验证。
- 典型代表是 `browser-use` 的 prompt 模式。

优点：

- 上手快。
- 对非工程人员更友好。
- 对页面变化的适应性可能更强。
- 容易覆盖探索式和视觉型任务。

缺点：

- 过程不可控时，团队会缺乏信任。
- token 成本高。
- 稳定性受模型表现波动影响大。
- 同一任务多次执行可能路径不同。

适合：

- 快速验证。
- 探索式测试。
- 页面结构变化频繁的阶段。

### 方案 C：Browser-use / Agent Browser + 固定场景脚本

核心做法：

- 底层仍是浏览器代理能力。
- 上层把测试场景固化成脚本或配置。
- 已有团队现状最接近这一类。

优点：

- 比纯 prompt 更可复用。
- 可以沉淀固定场景。
- 已经能做一键执行、报告输出。
- 便于快速搭出最小闭环。

缺点：

- 如果场景固化得太死，灵活性会下降。
- 如果脚本层过厚，又会回到传统脚本维护痛点。
- 文档和环境门槛容易压垮推广。

适合：

- 团队内部第一阶段验证。
- 已知关键路径场景。
- 需要“先跑起来”的阶段。

### 方案 D：MCP / IDE 集成式 AI 测试

核心做法：

- 通过 MCP 把测试能力接入 Claude、Cursor、IDE 或开发工具。
- 测试更靠近开发流，而不是单独平台。
- 典型参考是 `vibetest-use`、`web-eval-agent`。

优点：

- 更贴近开发者工作流。
- 适合开发阶段即时验证。
- 可与代码修改、日志、截图联合使用。
- 可自然接入“改代码 -> 跑测试 -> 看报告”的闭环。

缺点：

- 更依赖 IDE 生态。
- 非开发角色使用门槛仍然偏高。
- 工程实现通常比简单脚本更复杂。

适合：

- 前端开发自测。
- AI 编程协同。
- 本地开发闭环。

### 方案 E：一体化 AI 测试平台

核心做法：

- 提供场景管理、调度、历史、告警、报告、权限等完整平台能力。
- 典型参考是 `qa-use`。

优点：

- 适合团队协作和持续运营。
- 资产沉淀完整。
- 平台视角更强。
- 后期更容易扩展到组织级。

缺点：

- 研发成本高。
- 平台先行容易过重。
- 如果底层执行稳定性不足，平台价值会被拖垮。

适合：

- 中后期产品化。
- 多团队共享。
- 需要调度、历史和可观测性的场景。

## 关键判断

### 判断 1：团队不适合走“纯 AI 黑盒”主路线

两份会议纪要里反复出现的问题都是：

- 过程要看得见。
- 结果不能只看 pass / fail。
- 安装和执行路径要清楚。

这和纯黑盒代理天然冲突。因此，纯 AI 更适合作为能力层，而不是直接作为最终产品形态。

### 判断 2：团队当前最优路线是“混合型方案”

最佳平衡点不是传统脚本，也不是纯 prompt，而是：

- 场景文件负责复用和版本化。
- 最小执行器负责稳定动作。
- AI 负责规划、视觉判断、异常回退和报告整理。

这正好吻合 `需求.md` 中“像脚本一样读取文件执行”和“用自然语言控制验证”的双重诉求。

### 判断 3：先单机跑通，再平台化

从会议纪要看，当前真正卡住的不是平台能力，而是：

- 安装复杂。
- 文档不清。
- 新场景添加不够简单。
- 方案细节认知没有完全对齐。

所以现阶段重点不应该是 K8S、大规模调度、组织级平台，而是：

- 一键安装。
- 一键运行。
- 六个典型场景稳定跑通。
- 报告足够可信。

### 判断 4：报告能力不是附属功能，而是核心产品价值

团队多次强调“测试的核心是发现问题”，这意味着报告必须包含：

- 执行步骤。
- 截图 / 证据。
- 失败原因。
- 期望与实际差异。
- 问题优先级或问题分类。

如果只有 `pass/fail`，那这条产品线很难建立信任。

## 推荐路线

### 当前阶段推荐：方案 C + D 的组合

建议主线采用：

- 本地一键脚本作为入口。
- 场景文件作为资产形态。
- 浏览器最小执行器作为稳定基座。
- AI 作为截图理解、异常回退、报告生成层。
- 预留 MCP 接口，后续接入 IDE / Claude / Cursor。

这条路线的好处是：

- 能快速交付。
- 能被开发和测试人员使用。
- 不会马上掉进纯平台化的大坑。
- 保留未来产品化空间。

### 不建议当前阶段主推的路线

- 不建议只做传统脚本。
  原因是会重新回到维护成本问题。

- 不建议只做纯 AI prompt 测试。
  原因是稳定性、可见性和成本都不够可控。

- 不建议现在就先做重平台。
  原因是底层执行与场景资产尚未收敛，平台化会放大混乱。

## 下一步建议

### 1. 收敛成一个统一的对外描述

建议统一对内表述为：

“我们在做一个本地优先的 AI 自动化测试系统，支持用场景文件和自然语言描述测试目标，由稳定执行器完成基础动作，由 AI 完成视觉理解、异常回退和报告生成。”

### 2. 形成正式的三层架构共识

- 资产层：场景文件 / 测试用例。
- 执行层：浏览器执行器 / 桌面执行器。
- 智能层：AI 规划、视觉判断、报告整理。

### 3. 以“加一个新场景的成本”作为阶段指标

相比单次跑通，更应关注：

- 新同学能否按文档 30 分钟内安装完成。
- 新场景能否在半天内接入。
- 一次失败能否给出足够清晰的证据。

## 结论

基于当前文件夹里的全部材料，团队最适合的路线不是某个现成开源项目的直接照搬，而是采用“AI 编排 + 最小执行器 + 文件化场景 + 可见报告”的混合方案。

对比所有候选路径后，可以得出一个清晰结论：

- 传统脚本适合作为底座，但不应继续做成主交互方式。
- `browser-use` 一类项目提供了重要方向，但更适合作为能力参考而不是完整答案。
- 团队当前最值得做的，是把本地一键、场景复用、过程可见和报告可信四件事先做扎实。
