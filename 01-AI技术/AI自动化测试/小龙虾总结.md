# 小龙虾总结

## 说明

本文只保留技术探讨，基于以下两篇本地 clipping 整理：

- `Clippings/当小龙虾全面接管测试：80%测试人员的明天在哪里？.md`
- `Clippings/GPT-5.4、OpenClaw冲击波：未来2-3年内，80%的测试工程师会被裁掉？.md`

不再讨论岗位替代、行业趋势、职业转型等内容，只关注这套测试范式在技术上到底改变了什么。

## 核心结论

两篇文章共同描述的是一种从“脚本驱动的自动化测试”走向“目标驱动的自主测试”的技术转变。关键不在于模型会不会生成代码，而在于大模型已经能和 Computer Use、Agent 编排、MCP 工具、浏览器自动化、视觉识别、OCR、环境修复能力组合成一条完整执行链。

这条链路的结果是：

- 输入从脚本变成自然语言目标。
- 执行从固定步骤变成动态规划。
- 失败处理从直接报错变成自动尝试修复。
- 断言从 DOM 和选择器扩展到视觉与语义层。
- 输出从运行日志升级为结构化测试报告。

## 技术栈与能力拼装

从两篇文章里可以还原出一套较完整的技术组合。

### 1. 大模型作为“大脑”

模型承担的不是单一代码生成，而是完整任务理解与行动规划，包括：

- 理解自然语言测试目标。
- 拆解步骤。
- 判断当前执行结果是否符合预期。
- 在失败后重新规划下一步。
- 整理测试过程并输出报告。

在这个模式里，模型不只是“写一段 Playwright 代码”，而是持续参与整个测试回路。

### 2. OpenClaw / Agent 框架作为执行编排层

上一篇文章把 OpenClaw 描述成“管道”和“躯干”，它负责把模型能力接到真实环境里。按文中的说法，它主要体现为：

- 接收自然语言意图。
- 调度 Agent 执行具体任务。
- 把模型推理结果映射成对环境的操作。
- 支持多 Agent 协作。
- 给失败重试、反馈修正、持续执行提供运行框架。

这意味着测试系统不再是单个脚本文件，而更像是“模型 + 工具 + 执行环境”的协作系统。

### 3. MCP / Playwright 作为浏览器执行层

主文里多次提到 Playwright MCP。它承担的是浏览器与网页交互能力，包括：

- 启动浏览器。
- 打开页面。
- 输入查询。
- 点击链接和菜单。
- 等待页面加载。
- 截图。
- 获取页面上下文。

传统自动化里，这些动作通常由手写脚本精确控制；这里则变成模型按目标动态调用。

### 4. Vision / OCR 作为视觉断言层

文中的测试已经明显超出传统 DOM 自动化范围，原因是它依赖：

- 看懂页面布局。
- 在图片流中识别目标封面。
- 判断多个版本封面是否存在。
- 识别封面上的文字。
- 对截图结果进行验证。

这类任务说明断言已经不再只依赖元素定位，而是扩展到了“视觉对象识别 + 文字识别 + 语义比对”。

### 5. 环境修复与依赖安装作为自愈层

主文最关键的技术信号之一，是智能体并没有把环境问题交还给人处理，而是尝试自己解决，包括：

- 检查 Playwright 所需 Chromium 版本。
- 发现浏览器版本不匹配。
- 自动安装正确版本。
- 在 OCR 路径失败后尝试安装 `pytesseract`、`pillow`、`opencv-python`。
- 安装失败后切换到多模态识别方案。

这一点意味着执行系统不只是“跑测试”，而是具备了最初级的运行时自愈能力。

## 技术范式变化

### 从脚本驱动到意图驱动

传统模式是：

- 人工编写脚本。
- 显式指定定位器、等待逻辑、断言方式。
- 出错后回到代码层修脚本。

文章展示的新模式是：

- 人工给出目标。
- 模型自己规划路径。
- 工具负责执行动作。
- 模型根据结果继续迭代。

本质变化在于，测试系统关注的是“是否完成目标”，而不只是“是否逐行执行成功”。

### 从静态流程到动态重规划

在主文第一个案例里，截图位置错了之后，智能体不是整轮重跑，而是理解反馈并只修正出错部分。这个细节很重要，因为它说明测试执行不再是静态流水线，而是具备上下文连续性的动态过程。

第二个案例里，模型还会主动调整搜索策略，把模糊目标改写成“第1版 / 第2版 / 第3版”的更易执行查询。这说明它不仅在执行，还在主动降低问题难度。

### 从元素断言到视觉语义断言

文中很多任务若仅靠传统定位器非常痛苦，例如：

- 在大量图片中判断某几个封面是否存在。
- 根据封面图片识别版本。
- 截取正确对象而不是截整页。
- 对封面文字进行识别与保存。

这里真正起作用的是跨模态能力：

- 用视觉找到目标。
- 用语义理解目标描述。
- 用文本识别补足可验证信息。

这让测试从“能不能点到元素”扩展成“能不能理解页面上发生了什么”。

## 两个实战案例里的关键技术点

### 案例一：百度搜索 + 百科封面识别

任务链路可以拆成：

1. 启动浏览器并进入目标站点。
2. 执行搜索。
3. 识别搜索结果中的指定条目。
4. 点击进入详情页。
5. 找到目标封面。
6. 截图并保存。
7. 识别封面文字并保存文本。
8. 输出步骤、结果和结论。

这个案例主要暴露出 4 个技术点。

第一，浏览器环境检查与修复是自主完成的。系统发现 Chromium 版本不匹配后，会自行修正，而不是把错误停留在依赖层。

第二，执行结果可以被人类反馈回路修正。截图错误后，用户只描述“哪里不对”，系统就能根据语义反馈重做局部步骤。

第三，OCR 不是唯一方案。路径 A 失败后，系统会切换到路径 B，这种多方案回退是典型的 Agent 行为，不是普通脚本行为。

第四，最终产出是面向结果的报告，不是单纯的控制台输出。这说明“执行层”和“汇报层”已经被整合在一个 Agent 回路里。

### 案例二：图片搜索中的多版本封面识别

第二个案例的技术挑战更集中：

- 目标对象不是标准页面元素，而是图片内容。
- 用户没有给封面特征，只给了版本名称。
- 需要在大量干扰项中完成目标筛选。
- 还要对每个目标继续截图和文字识别。

这个案例说明了 5 个能力：

第一，模型具备较强的语义归一化能力。它把《全程软件测试》理解成第一版，而不是卡死在字面不一致上。

第二，模型具备视觉筛选能力。它能在图片流里把无关图片排除掉，找到目标封面。

第三，模型具备任务分解能力。它会把“判断存在”拆成搜索、比对、打开、截图、识别等子步骤。

第四，模型具备策略优化能力。它会自己改写查询方式，以更稳妥地完成目标。

第五，模型具备结果整理能力。即使实际寻找顺序不是 1、2、3，它仍然可以按更适合阅读的顺序输出结果。

## 从两篇文章中抽出的技术工作流

如果把文中描述统一成一条工程链路，大致是这样：

1. 用户用自然语言给出测试目标与验收条件。
2. 模型把目标拆成可执行步骤。
3. Agent 框架把步骤分发给工具层。
4. MCP / Playwright 执行页面操作。
5. Vision / OCR 对页面和截图做补充识别。
6. 模型根据执行结果决定继续、修正、重试或换方案。
7. 所有步骤被整理成结构化结果输出。

这里最重要的不是任何单个组件，而是“闭环”：

- 有目标。
- 有操作。
- 有观察。
- 有判断。
- 有纠错。
- 有结果整理。

传统自动化通常只覆盖“操作”，而这套体系试图覆盖完整闭环。

## 相比传统自动化测试，技术上到底变了什么

### 传统自动化的核心约束

- 强依赖定位器。
- 强依赖稳定页面结构。
- 强依赖人工处理环境与依赖。
- 失败后主要靠人修脚本。
- 很难处理图片、视觉布局、模糊对象查找。

### 新范式的核心增量

- 可以直接从目标描述出发。
- 可以把页面当作视觉对象而不只是 DOM 树。
- 可以把失败当作中间状态而不是终止状态。
- 可以在多种工具与多条策略之间切换。
- 可以把执行和报告统一在一个任务里完成。

因此，文中的重点并不是“AI 替代了 Playwright”，而是“AI 把 Playwright 从脚本 API 变成了可被推理系统动态调用的执行器”。

## 当前技术边界

如果只谈技术，不谈行业，文中仍然暴露出一些明显边界。

### 1. 依赖外部环境

OCR 安装失败、浏览器版本不匹配、网络下载失败，这些都说明系统仍然受真实环境影响。只是区别在于，文章里的智能体已经开始尝试自己吸收这些波动。

### 2. 任务成功依赖目标表达质量

案例能成功，一个重要原因是目标足够明确：要找哪个页面、哪个封面、输出什么文件、要什么结论。目标越模糊，系统越容易走弯路。

### 3. 视觉推断仍然可能出错

第一次截图截错就是直接例子。也就是说，视觉能力虽然强，但并不是稳定到可以完全跳过人工复核。

### 4. 工具链切换需要足够的策略能力

从 OCR 失败到改用多模态识别，这种切换背后依赖的是模型的推理与工具使用能力。如果模型不会切、不会想备选路径，那么系统仍会卡住。

## 总结

两篇文章合起来，技术上最值得关注的不是某个单点能力，而是测试系统开始具备了“自主闭环”特征：它能理解目标、操作环境、观察结果、修正错误、切换方案，并最终给出结构化输出。

用更凝练的话说，这套体系把测试从“人写脚本驱动工具”推进成了“模型驱动工具围绕目标持续行动”。这正是文中“小龙虾”最核心的技术意义。
