# 产品预言报告

## 说明

这里的“产品预言”不按空泛行业趋势来写，而是基于当前目录内材料，对这条产品线未来最可能长成什么样做产品判断。

## 判断基础

这份判断来自 5 类输入：

- `需求.md` 提供了最原始的用户诉求。
- `3.11会议纪要.md` 暴露了传统脚本路线和纯 AI 路线的真实争议点。
- `3.18会议纪要.md` 体现了第一轮原型后的实际落地问题。
- `前端 AI 自动化测试：brower-use 调研.md` 给出了外部竞品和生态参考。
- `小龙虾总结.md` 给出了这类系统最核心的技术范式变化。

## 最核心的产品判断

### 判断 1：这不会先成为“替代 QA 的平台”，而会先成为“开发与测试共用的本地验证助手”

从现有材料看，最真实的痛点不是组织级管理，而是：

- 手工回归重复。
- 脚本维护太重。
- 新场景添加太慢。
- 问题定位证据不完整。

所以产品最先击中的用户，不会是大而全的测试管理部门，而是：

- 前端开发自测。
- 测试同学做高频回归。
- 产品 / 项目同学做关键路径验证。

它最先提供的价值也不是“替代人”，而是：

- 让重复验证成本下降。
- 让发现问题的过程被标准化。
- 让场景执行和问题证据一起沉淀。

### 判断 2：产品入口会从“写代码”转向“写场景”

`需求.md` 已经非常明确，希望：

- 用自然语言控制功能操作。
- 还能像脚本一样读取文件自动执行。

这意味着最终稳定的产品入口，大概率不是 TS / Python 脚本，而是场景文件，例如：

- Markdown 场景描述。
- YAML / JSON 场景规范。
- Prompt 模板 + 参数。

也就是说，产品最重要的资产会从“脚本资产”变成“场景资产”。

### 判断 3：用户真正购买的不是“会操作浏览器”，而是“可信的问题报告”

如果只能自动点击、自动输入、自动截图，这还只是能力演示，不是产品闭环。

从会议纪要里可以看出，团队更在意的是：

- 是否发现了真正的问题。
- 是否能说明问题发生在哪一步。
- 是否能给出足够证据。
- 是否方便团队协作和复现。

所以这个产品的真正价值中心会逐渐转向：

- 结构化 bug 报告。
- 可回放的执行轨迹。
- 期望 / 实际差异对比。
- 场景历史与回归对照。

### 判断 4：单机一键体验会比平台化能力更早决定产品成败

3.18 会议纪要里最明显的问题不是“功能不够多”，而是：

- 环境依赖不清楚。
- 安装配置不透明。
- 方案讲不清楚。
- 新场景接入不够简单。

因此，产品早期成败更可能取决于：

- 一键安装。
- 一键运行。
- 一键看结果。

而不是：

- 权限系统。
- 多租户。
- 大规模调度。
- 复杂工作台。

### 判断 5：纯 AI 产品形态不会赢，混合型产品形态会赢

从现有材料能看出两条路线都不完整：

- 纯脚本路线可控，但维护痛苦。
- 纯 AI 路线灵活，但不够稳、成本高、过程不透明。

因此真正可持续的产品形态会是“混合型”：

- 常规动作交给稳定执行器。
- 非结构化任务交给 AI。
- 失败时由 AI 辅助回退和补充判断。
- 最终所有信息都沉淀为统一报告。

这个判断基本贯穿了当前全部材料。

## 未来 12 个月最可能的产品形态

### 形态 1：本地测试 Copilot

最先跑出来的形态，大概率是一个本地优先工具，而不是平台：

- 用户选一个项目。
- 运行一条命令或一个按钮。
- 读取场景文件。
- 自动执行浏览器操作。
- 生成截图、日志和 Markdown / HTML 报告。

这是最符合当前团队节奏和材料信号的版本。

### 形态 2：IDE / Claude / Cursor 插件化入口

随着底层能力稳定，这条产品线很自然会往 IDE 集成方向延伸：

- 开发改完代码后直接触发 AI 测试。
- 在 IDE 内查看执行过程和报告。
- 用自然语言补充或调整测试目标。
- 通过 MCP 接入更通用的 AI 开发工作流。

这与外部生态 `vibetest-use`、`web-eval-agent` 的方向一致，也符合会议纪要里“开发过程全流程验证”的诉求。

### 形态 3：轻平台，而不是重平台

如果产品继续演进，先长出来的不会是很重的企业级平台，而会是一个轻平台：

- 场景管理。
- 历史记录。
- 报告检索。
- 定时任务。
- 邮件 / IM 通知。

也就是 `qa-use` 那类能力的一部分，但会在底层能力稳定之后再补，而不是先做。

## 产品应该优先服务谁

### 第一优先：前端开发

原因很直接：

- 他们最痛于 UI 测试和回归。
- 他们就在本地环境里工作。
- 他们能最快接受 IDE / MCP / CLI 工具形态。
- 他们对“改完代码顺手验证一下”最敏感。

### 第二优先：测试同学

他们的价值不在于被替代，而在于：

- 快速沉淀高频场景。
- 复用验证逻辑。
- 让问题报告更完整。
- 将手工验证转成可重复流程。

### 第三优先：产品 / 项目同学

对他们而言，最有吸引力的不是复杂配置，而是：

- 选场景。
- 看报告。
- 对结果提问。

但这个阶段应该稍后于开发与测试，因为他们对安装与调试容忍度最低。

## 产品最可能的核心功能

### 必备功能

- 场景文件读取执行。
- 浏览器自动操作。
- 截图和步骤记录。
- 失败证据沉淀。
- pass / fail + 问题详情报告。
- 一键安装与环境自检。

### 让产品真正拉开差距的功能

- 视觉断言。
- 自然语言补充断言。
- 执行失败后的自动重试与策略切换。
- 报告中的问题归类与优先级建议。
- 历史结果对比。

### 暂时不该重投入的功能

- 重平台权限体系。
- 大规模分布式调度。
- 很复杂的 SaaS 管理台。
- 过早支持太多非核心执行环境。

## 产品路线判断

### 阶段一：把“能跑”变成“敢用”

这个阶段的关键词不是智能，而是可信。

目标应该是：

- 安装简单。
- 执行可见。
- 结果清楚。
- 场景可复用。

### 阶段二：把“敢用”变成“高频用”

这个阶段的关键词是低门槛。

需要解决：

- 添加新场景更简单。
- 报告更容易消费。
- IDE 内就能触发。
- 支持更多测试模板。

### 阶段三：把“高频用”变成“资产化”

这个阶段的关键词是沉淀。

包括：

- 场景库。
- 模板库。
- 历史结果。
- 问题模式归档。
- 团队共享和回归调度。

## 这条产品线最大的风险

### 风险 1：看起来很智能，但实际不可信

如果报告不能自证过程，用户很快就会失去信任。

### 风险 2：看起来比 Playwright 简单，实际上更难装

从会议纪要看，这已经是现实风险，不是理论风险。

### 风险 3：为了追求灵活，牺牲复用性

如果每次都是重新写 prompt，最终就无法形成团队资产。

### 风险 4：为了追求平台感，过早做重产品

一旦底层执行和场景资产还不稳定，平台越重，失败体验越明显。

## 成功后的产品会长成什么样

如果这条线做成，一个比较可信的产品形态会是：

- 用户不必写脚本，但能维护场景文件。
- 执行过程全程可见，可截图、可回放、可解释。
- 测试结果不只告诉你过没过，而是告诉你哪里坏了、证据是什么。
- 新场景接入成本显著低于传统端到端测试。
- 开发在本地就能把高频验证自动化完成。

## 一句话预言

这条产品线最有可能成功的方向，不是“一个替代 QA 的大平台”，而是“一个本地优先、场景驱动、AI 辅助、报告可信的测试执行与问题发现工具”。
