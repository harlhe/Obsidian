#### 介绍一下ReAct范式和Plan and Execute范式
ReAct和Plan&Execute是两种主流的Agent推理架构。

**ReAct范式：**
目前最常用的Agent架构，它将CoT与特定于任务的动作结合在一起。在ReAct范式下，模型会**交替生成**Thought思考和Action行动。
指令流程分为四步：
- Thought：模型分析当前任务，思考下一步该怎么做
- Action：模型选择工具并执行
- Observation：模型观察工具返回的结果
- 循环：根据观察结果，重复上述步骤，直到得出结论
优点：
- **动态调整**：能根据每一步的反馈实时修正策略。
- **容错性强**：如果一次工具调用出错，模型可以在下一步尝试修复。
缺点：
- Token消耗高，每一步都需要把历史喂给模型。
- 容易死循环：模型可能在两个错误动作上反复横跳，或者在试错道路上越走越远。容易受单步观察结果干扰产生偏移

Plan and Execute范式：
这种范式解耦了规划和执行，将复杂任务先进行拆解，然后再逐一解答。核心逻辑是将Agent拆分为两个角色——规划者和执行者。
执行流程：
- Planning：Planner 接收任务，一次性生成一个完整的子任务列表（Step 1, Step 2, ...）。
- Executing：Executor 按照清单，依次调用工具完成任务。
- Re-planning(可选)：在执行完清单后，模型根据结果判断是否需要重新规划。
优点：
- **逻辑清晰**：更适合处理步骤极多、逻辑复杂的长链任务。
- **并行潜力**：如果子任务之间没有依赖关系，可以同时执行，大幅降低延迟。
缺点：
- **刚性较强**：如果在第一步就遇到了预料之外的错误，后续的计划可能全部失效。容易因初期规划不周导致后期全面溃败

#### 什么情况下用ReAct？什么情况下用Planning and Execute？
ReAct适合不确定的、交互探索式的任务，Planning适合确定性强、结构化、多步骤的任务。

ReAct的本质是**探索**，强调不确定性，适合：
- 高不确定性任务：例如网络搜索，无法预知搜索结果的第一条链接是否有用。Agent 需要看完第一页的内容，才能决定是点进去阅读，还是修改关键词重搜。
- 需要实时交互的环境：例如数据库查询与纠错，当 Agent 写了一个 SQL 语句执行报错时，ReAct 能捕捉 Error 信息，在下一轮思考中修正语法。
- 任务链路短但逻辑复杂：每一步都需要极强的逻辑推理来支撑决策，并且链路短token消耗低。
- 容错要求高：因为每一步都有 `Thought` 环节，模型可以发现之前的错误并进行“自我修复”。

Plan and Execute的本质是**编排**，强调预见性与执行效率，适合：
- 长链路、多步骤、流程固定的任务：如软件开发Agent，需要先写架构设计 -> 定义接口 -> 写逻辑代码 -> 写单元测试。这种流程通常非常固定，不需要走一步看一步。
- 对响应速度敏感的任务：由于 Planner 已经生成了任务清单，如果任务之间没有依赖（例如：同时查询 3 个不同城市的温度），Executor 可以**并行**调用工具，这比 ReAct 的串行推理快得多。
- 确定性和可预测性的场景：在工业化流水线中，我们希望 Agent 的行为是可预测的。预先生成的 Plan 方便人工或代码审计，可以在执行前拦截不合理的计划。
- 对token成本敏感：ReAct 在每轮循环都要带上之前所有的 Thought/Action/Observation，Context 呈阶梯式暴涨。Plan-and-Execute 的 Executor 往往只需要关注当前的子任务，能有效节省 Context 空间。

在实际的大型Agent项目中，一般是两者结合。
- 上层使用Planning进行大目标拆解。
- 底层针对拆解后的某些合适的子任务，使用ReAct来执行工具调用。

对于 Plan-and-Execute 架构，可以在推理引擎层利用其子任务并行的特性，通过 Continuous Batching 和 CUDA Graph 显著提升多个 Executor 并发执行时的吞吐量。

#### 介绍一下Multi-Agent？是如何共享上下文的？子Agent会使用父Agent的所有Context吗？
Multi-agent 系统是由多个独立的 Agent 组成的协作网络。每个 Agent 通常被赋予特定的角色（Role）、人格（Persona）和工具集（Tools）。
主要目的是通过分工降低单个LLM的推理压力。
协作模式一般分为三种：
- 层级式（Hierarchical）：有一个 Leader Agent 拆解任务并分发给 Worker Agents（类似于 Plan-and-Execute 的升级版）。
- 协作式（Joint Collaboration）：Agent 之间像对话一样轮流发言。
- 流水线式（Sequential）：A 做完传给 B，B 做完传给 C。

上下文共享并不是简单的内存共享，通常有三种交换信息的方式：
1. 公共黑板模式：所有 Agent 共享一个全局状态对象。Agent A 将处理结果写入 `State`，Agent B 从 `State` 中读取。信息透明，所有 Agent 都能看到进度。
2. 消息传递模式：Agent 之间像发邮件一样传递信息。Agent A 的输出（Response）直接作为 Agent B 的输入（Prompt）的一部分。解耦性强，Agent 只需要关注发给自己的信息。
3. 总结上下文传递：为了节省 Token 和避免干扰，不传递原始对话，而是传递**摘要**。由一个专职的“摘要 Agent”不断总结当前的协作进度，并将摘要发给下一个 Agent。

子Agent会用父Agent的所有Context吗？
不建议共享。
- 噪声幻觉：子Agent如果共享了父Agent的Context，很容易受到噪声干扰产生幻觉。
- token消耗：如果所有子 Agent 都承载完整的父级上下文，Token 消耗会呈几何倍数增长。很快就会触及 LLM 的 `Context Window` 上限，导致推理变慢甚至失败。
- 记忆损耗：当上下文过长时，LLM 对中间部分信息的提取能力会大幅下降。
在工程上，一般采用上下文裁剪的方式控制父子Agent的Context：
- 按需分配：父 Agent 只将与该子任务相关的指令（Task Description）和必要的变量（Variables）传给子 Agent。
- 状态隔离：子 Agent 拥有自己的局部上下文，只有当它完成任务并返回结果时，结果才会合并回主上下文（Global Context）。
- RAG 辅助检索：父 Agent 的海量上下文存入向量数据库，子 Agent 根据需要自行检索相关片段，而不是全量接收。

推理优化：
在 Multi-agent 场景下，频繁的上下文切换（Context Switch）和冗余的 Prompt 会导致推理延迟。在 **Nano-vllm** 中，可以通过 **Prefix Caching（前缀缓存）** 技术，将父 Agent 共享的系统提示词（System Prompt）和公共背景部分的 KV Cache 缓存起来。这样当多个子 Agent 并行启动时，可以复用这部分缓存，极大降低 TTFT（首字延迟）并节省显存。

#### 场景题：现在需要设计智能客服Agent，根据用户的提问来进行尽可能准确的回答，你觉得该如何设计？需要考虑哪些方面？
智能客服的目的是准确性和服务闭环，单纯靠LLM的Chat能力是不够的，因为客服解决的可能是专业领域的内容。必须构建一套结合了 RAG、工作流编排以及自我反思机制的架构。

首先是架构的选择，需要Plan和ReAct混合架构。
1. 意图识别层：
	功能：对用户提问进行分类，比如是咨询产品、订单查询、单纯闲聊、故障报修。
	实现：利用 LLM 配合少量示例（Few-shot）或语义向量匹配，将用户引导至不同的处理子流。
2. 知识执行层：
	根据意图进入不同的处理流。
	- RAG咨询类：从企业知识库中检索 PDF、文档片段，生成基于事实的回答。
	- Tool-Use模式/固定业务类：例如查询订单、重置密码等调用固定API接口。
	- ReAct模式：复杂纠错，当用户提问模糊或工具返回异常时，进行多轮追问和推理。
3. 质量门禁层：
	- 回答在发给用户前，先进行自我检查。模型自检“回答是否包含敏感词？”、“回答是否参考了检索到的文档？”。这一层应该给出大量的antipattern。
	- 如果对回答时间不敏感而对正确性敏感，这一层还可以再用Plan and Execute模式进行并发的checklist检查。

关键考察维度：
1. 准确性
	- 混合检索 (Hybrid Search)：结合向量搜索（**语义**）和传统关键词搜索（**BM25**），确保能搜到特定产品型号或专有名词。
	- **Prompt 工程**：在 System Prompt 中加入：“如果你不确定答案，请引导至人工客服，不要编造事实。”
	- 知识库更新：建立 Hot-update（热更新） 机制，确保 Agent 能获取最新的促销信息或政策。
2. 上下文管理
	- 对话压缩：客服对话往往很长。利用底层优化思路，只保留最近的 N 轮对话，并对更早的对话进行 Summary（摘要） **压缩**存储。
	- 多轮追问 (Slot Filling)：当用户说“查下我的订单”时，Agent 应具备“填槽”能力，如果缺失信息，主动询问“请提供您的订单号或手机号”。（这好像没啥用？LLM自己就可以解决吧）
3. 响应延迟
	- 流式输出 (Streaming)：让用户先看到第一个字，减少焦虑。
	- KV Cache 复用：客服系统存在大量重复的 System Prompt 和知识片段。在推理端（如你研究的 Nano-vllm）使用 Prefix Caching，可以大幅缩短首字延迟。
	- **PD 分离**，或者设置PD 优先级。
4. 幻觉控制
	- 知识召回率检测：如果向量库召回的分数（Score）低于阈值，直接转人工或返回预设话术。
	- 双重验证：让模型将生成的答案与原始参考文档进行核对（NLI，自然语言推理）。
5. 评估体系：
	- 离线评测 (Ragas/TruLens)：构建黄金数据集，自动评估 RAG 的检索准确度和生成质量。
	- 在线反馈 (RLHF Lite)：用户点击“点赞/点踩”后，将数据闭环喂给模型微调或 Prompt 优化。

#### 如何避免这个场景下模型的幻觉问题？
1. 检索阶段：RAG 优化
	幻觉往往是因为模型在“没搜到”或“搜错了”的情况下强行解释。
	- **混合检索（Hybrid Search）**：结合语义搜索（Embedding）和关键词搜索（BM25）。防止模型在遇到“产品型号（如 Z7 II）”或“技术参数”等专有名词时，因向量空间距离过远而召回失败。（RAG 的八股要单独开一个文档，不然看不懂）
	- **重排序（Rerank）**：初步召回 20 个片段，再用一个 Cross-Encoder 模型进行二次打分，选出最相关的 3-5 个。（这也是 RAG 的八股）
	- **上下文清洗**：剔除检索片段中的 HTML 标签、冗余广告等噪声，降低模型被干扰的概率。
2. 生成阶段：
	通过 Prompt Engineering 和输出模式限制模型的发挥。
	- **引用强制（Citations）**：要求模型在回答的每一句话后面标注来源，如 `[1]`。如果模型发现找不到来源，它会更倾向于拒绝回答。
	- **拒绝回答机制（Out-of-Distribution Handling）**：明确告知模型：“如果提供的文档中没有答案，请直接回答‘抱歉，我目前的知识库中没有相关信息’，严禁根据常识猜测。”
	- **CoT 引导**：让模型先提取文档中的关键事实，再根据事实生成回答，而不是直接输出结论。
3. 后处理阶段：质量门禁层检查
	- **NLI（自然语言推理）验证**： 启动一个专门的小模型（或另一路 LLM 调用），判定生成的 `Answer` 是否能被召回的 `Context` 所蕴含（Entailment）。如果判定为“矛盾”或“中立”，则拦截。
	- **Anti-pattern 匹配**： 利用你提到的 Anti-pattern 库，检测回答中是否出现了典型的幻觉特征词（如“据我所知”、“可能”等含糊词汇，或不在库中的虚假 URL）。
	- 并行验证：利用 **Plan-and-Execute** 进行并发检查。这里由于多个检查的输入基本一致，可以利用Prefix Caching进行推理优化。

#### 如果用户提问是一个逻辑陷阱，Agent会如何反应？
自己追加的问题，不在面经里。
如果提问不合理，应该设计拦截的逻辑。拦截分为在RAG前的拦截与生成后的拦截。
**第一步：负向 Prompt 与 拒绝机制（前置）**
在系统提示词中预设逻辑：_“如果用户询问的功能不在已知清单内，请回答‘本产品暂不支持该功能’。”_ 这种方式配合 **Router** 能拦截 80% 的低级陷阱。

**第二步：带权重的 RAG 召回（执行中）**
在检索时，如果相似度分数（Similarity Score）低于某个极高的阈值，系统不进入生成逻辑，而是直接转入“澄清提问”环节：_“您是指 XX 功能吗？我没能找到您提到的 YY 功能。”_

**第三步：幻觉检测与 Checklist 审计（后置）**
针对剩下的 20% 隐蔽陷阱（例如用户利用逻辑推理诱导模型承认某个功能存在），利用你提到的 **Plan-and-Execute 模式进行 checklist 检查**。
- **检查项：** “回答中的功能名称是否出现在检索文本中？” -> 如果为 False，立即触发纠错。

在验证时，为了不牺牲用户体验，避免时延过高，可以采用**投机执行**的策略。
当用户提问时，同时并行启动两条链路：一条是快速的**意图校验链路**（小模型/规则），另一条是**主生成链路**。如果校验链路在 50ms 内判定为逻辑陷阱，就直接 **Abort（终止）** 主生成链路正在运行的 KV Cache 计算和文本生成任务。

#### 对于这样的Agent服务，电商大促的时候，流量大，有流量尖刺的情况下，如何解决？
电商大促是高并发、高弹性、低延迟的需求，Agent系统的瓶颈主要在显存资源、推理吞吐量、下游API承载力上。
一、架构层面的流量削峰
1. 异步队列与优先级调度：
	- 接入层流控：使用 Redis 或消息队列（MQ）缓冲请求。大促期间，根据用户等级（如 VIP）或任务类型（如售后投诉优先级高于闲聊）进行优先级调度。
	- 平滑请求：当流量尖刺到达阈值时，触发限流（Throttling）或排队机制，宁可让用户看到“小二正在赶来”，也不要让 GPU 显存 OOM。
2. 动态降级
	- **模型降级**：流量峰值时，将部分简单的意图识别任务从大模型（如 GPT-4）切换为更小的模型（如 Qwen-7B）或精调过的 BERT/FastText。
	- **链路降级**：关闭非核心功能。例如，暂时关闭复杂的“质量门禁并发检查”，改为基于关键词或启发式规则的快速校验，牺牲部分准确性换取系统存活。

二、Agent层面的优化
1. 结果缓存（Semantic Cache）
- **原理**：大促期间，用户的问题重复率极高（如“XX 活动怎么领券？”）。
- **实现**：建立**语义缓存层**（如使用 GPTCache 或向量库）。当新提问的语义向量与已回答问题的相似度极高时，直接返回缓存结果，完全跳过 LLM 推理。
2. 投机推理（Speculative Decoding）
- **原理**：用一个小模型（草稿模型）快速预生成几个 Token，再用大模型一次性校验。
- **效果**：在不改变最终输出质量的前提下，降低推理延迟。

还可以答一下推理层面优化：连续批处理、Paged+KVCache、Prefix Caching

#### SSE和WebSocket的区别？
SSE是基于**HTTP**的**单向**推送技术。服务器可以向客户端连续发送数据流，而不需要客户端反复请求。数据格式是文本流，通常是text/event-stream。
WebSocket是独立的、基于**TCP**的协议，实现**全双工通信**。数据格式是二进制或文本。

|**特性**|**SSE**|**WebSocket**|
|---|---|---|
|**方向性**|单向（服务器推送）|双向（全双工）|
|**连接维护**|基于标准 HTTP，支持自动重连|独立协议，重连需手动实现|
|**防火墙友好度**|极佳（标准 80/443 端口）|一般（部分严格防火墙可能拦截）|
|**轻量级**|非常轻量，开销小|协议握手较复杂，相对较重|
|**最大连接数**|浏览器有限制（HTTP/1.1 下 6 个）|受限于服务器内存和文件描述符|
|**消息类型**|仅文本|文本 + 二进制|
为什么大模型流式输出经常用SSE？
- **契合生成模式**：AI 生成内容本质上是“用户发一次请求（Prompt），服务器持续输出（Tokens）”。这种一问一答且回复较长的场景，**单向流**完全够用。
- **HTTP 兼容性**：SSE 本质就是 HTTP 请求，可以轻松通过 Nginx 转发、负载均衡，且天然支持 **HTTP/2 头部压缩**。
- **开发效率**：前端原生支持 `EventSource` 接口，后端实现逻辑简单，非常适合将推理引擎（如你的 **Nano-vllm**）生成的 Token 实时泵回前端。
