### 总结

|模型|是否双向？|解释|
|---|---|---|
|**经典RPC (如HTTP/1.1上的JSON-RPC)**|**不是** (从角色和发起权角度)|角色固定，永远由客户端发起请求，服务器只能响应。|
|**现代RPC (如gRPC的双向流)**|**是**|连接建立后，双方可以随时、独立地向对方发送消息。|
|**特定传输上的RPC (如WebSocket上的JSON-RPC)**|**是**|底层传输协议（WebSocket）是双向的，允许任何一方随时发起RPC请求。|
### 核心区别对比表

|特性|gRPC|SSE (Server-Sent Events)|
|---|---|---|
|**核心概念**|**RPC (远程过程调用)**|**服务器推送事件 (Server Push)**|
||客户端像调用本地函数一样调用远程服务器上的函数。|服务器在一个持久连接上，持续不断地向客户端发送事件消息。|
|**通信方向**|**灵活，支持四种模式**：<br>1. 单向 (请求-响应)<br>2. 服务器流<br>3. 客户端流<br>4. **双向流**|**严格单向** (Server -> Client)|
||客户端发起连接后，双方都可以向对方发送数据流。|客户端发起连接后，只有服务器可以向客户端发送数据。|
|**底层协议**|**HTTP/2**|**HTTP/1.1**|
||二进制协议，支持多路复用、头部压缩，性能高。|文本协议，有队头阻塞等限制。|
|**数据格式**|**Protocol Buffers (Protobuf)** (默认)|**纯文本 (UTF-8)**|
||二进制、结构化、需要预先定义 Schema (`.proto` 文件)。数据紧凑，序列化速度快。|文本格式，通常使用 JSON。人类可读，但相对冗长。|
|**主要用途**|**微服务间通信**、移动端与后端通信、需要高性能和双向流的场景。|**向Web浏览器推送更新**，如新闻订阅、状态更新、股票行情、**LLM打字机效果**。|
|**复杂性与生态**|相对复杂，需要特定的工具链（`protoc`编译器）和库支持。|非常简单，浏览器原生支持 `EventSource` API，后端实现也很直接。|
