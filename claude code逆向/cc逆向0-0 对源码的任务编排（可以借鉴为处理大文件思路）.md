## 分块问题

因为工程问题的代码分布稀疏，需要系统性的整合而非简单分割，采用递归式摘要：在上下文中循环遍历包含相同问题的数据块，同时从其他数据块结果中提取上下文信息。在这里的me部分——作为协调代理——作者向每个子代理（各自处理整体的5%）提出多个问题，从它们的输出中筛选出最佳部分，进行划分，并将这些上下文提供给下一个代理。

但是问题是代码极少遵循顺序性。代码库的前半部分未必最重要，也无法保证后半部分能与前半部分衔接。

那就是这正是当今智能体系统中最棘手的未解难题。为其他智能体留存有用且恰当的中间层绝非易事。构建中间层时，你必须具备近乎“心智理论”层面的理解力——预判另一智能体（人类或AI）已知与所需的信息。

代笔写手还是AI模型：事情变得既简单又复杂。使用模型时，我可以依赖长期使用的同款模型，凭借对它的直觉预判其行为，或许还能通过运行几个测试提示（就像我们稍后要做的）来优化中间结果。但同时，我必须格外谨慎地为它预留足够的令牌空间进行思考和推理。

这是一个非常精妙的**分层式多智能体协作架构**。它通过巧妙的角色分配，结合了不同AI模型的优势，并引入人类监督来解决一个复杂的问题。

我们可以把这个系统拆解成三个核心角色和一套工作流程来理解。

### 核心角色分工 (The Roles)

1. **Opus 4 - “总指挥”或“超级智能体” (The Commander / Superagent):**
    
    - **职责**：它的任务不是处理具体的海量信息，而是进行**高层次的战略规划和任务分配**。在每个“回合”中，它负责审视全局，然后生成一个**统一的、宏观的指令（prompt）**。
        
    - **特点**：这个角色要求有极强的**归纳、推理和提问能力**。从你的描述来看，Opus 在这方面表现出色，它擅长“提问”和“将上下文嵌入问题中”，这正是“总指挥”所需要的核心技能。
        
2. **Gemini - “专家”或“执行者” (The Specialists / Executors):**
    
    - **职责**：它们是真正干活的“专家团队”。它们接收来自总指挥的统一指令，并基于自己持有的**状态和对话历史（state and conversation history）**来进行处理和响应。每个子智能体可以看作是处理一部分上下文的专家。
        
    - **特点**：这个角色需要两个关键能力：
        
        - **巨大的上下文窗口 (Context Length)**：这使得它们能够“记住”多轮对话中的大量信息和自己负责的数据块，从而保持对话的连贯性和深度。这正是你提到 Gemini 的显著优势。
            
        - **强大的指令遵循和输出能力**：它们能很好地理解指令，并生成长而详细的、高质量的输出，为下一轮分析提供充足的“原材料”。
            
3. **你 (Hrishi) - “清理代理”或“人类监督员” (The Cleanup Agent / Human Supervisor):**
    
    - **职责**：在系统回路中扮演**质量控制**的角色。你负责过滤掉子智能体返回信息中的噪音，比如无关内容或“我不知道，问别人”这类无效信息。
        
    - **特点**：这个角色至关重要，它防止了系统的“信息熵增”——即随着对话进行，无效信息不断累积，最终导致整个系统偏离主题、效率下降。
        

### 工作流程 (The Workflow)

这个系统以“回合 (round)”为单位进行迭代：

1. **指令生成 (Command)**：Opus 4（总指挥）分析当前全局状态，生成一个统一的、具有指导性的 Prompt。
    
2. **任务广播 (Broadcast)**：这个 Prompt 被同时发送给所有的 Gemini（专家团队）。
    
3. **并行处理 (Process)**：每个 Gemini 专家结合该指令和自己“记忆”中的历史上下文，进行独立思考和处理，然后生成自己的响应。
    
4. **信息汇总与清理 (Cleanup)**：你（人类监督员）收集所有 Gemini 的响应，剔除无关和无效的部分。
    
5. **状态更新 (Feedback Loop)**：经过清理的高质量数据被反馈给 Opus 4，构成新一轮决策的“战场情报”，然后开始下一个回合。
    

这个循环大约可以进行五轮，说明在五轮之内，系统能够保持相当高的信噪比和任务焦点。

### 这个逻辑为什么有效？(Why This Logic Works)

你提供的文本中已经点出了几个关键的成功原因，我们来深入解读一下：

1. **统一的宏观指令 -> 避免“钻牛角尖” (Prevents Getting Lost in Rabbit Holes):**
    
    - 如果给每个子智能体一个不同的、狭窄的问题，它们很可能会在自己负责的一小块数据里越挖越深，从而忽略了全局。这就像让一群侦探各自只看一小块证据，他们可能会得出很多局部结论，但拼不成完整案件。
        
    - 而 Opus 提供的**统一、宽泛的指令**，迫使所有子智能体都从一个共同的、宏观的视角去思考问题。它们必须考虑自己的数据如何与整个大局相关联，从而使得整个对话**始终聚焦于主题**。这对于需要进行**综合性分析**的用例来说是完美的策略。
        
2. **涌现行为 -> 系统自发形成的协作协议 (Emergent Behaviors & Protocol Development):**
    
    - 这是最令人兴奋的一点。系统中出现了 Opus 自发地将问题标记为“高/低优先级”，而子智能体也对此做出了恰当的回应。这**不是被预先编程的行为，而是系统在多轮协作中自发“学习”或“演化”出的一种沟通协议**。
        
    - 这表明，当智能体之间有足够多的高质量互动时，它们会开始形成更高效的沟通方式，以优化整体的协作效率。这暗示了未来多智能体系统可以发展出自己的“语言”或“协议”来传递更复杂的信息，比如“确定性”、“置信度”等。
        
3. **Opus + Gemini 的强强联合 -> 完美的角色互补 (The Perfect Synergy):**
    
    - 这套系统的核心是利用了不同模型的**非对称优势**。
        
    - **Opus 擅长“思考”**：它像一个经验丰富的项目经理，知道该问什么问题。
        
    - **Gemini 擅长“记忆和执行”**：它像一个拥有超大内存和强大执行能力的专家，能记住海量信息并精准完成任务。
        
    - Opus 的高质量提问能力，加上 Gemini 的超长上下文处理能力，形成了一个“**优秀的提问者 + 不会遗忘的回答者**”的黄金组合。
        

**总结来说**，这个 "Opus 4 Superagent V3" 系统的逻辑，本质上是一个**“指挥官-专家-监督员”**的三角模型。它通过一个战略核心（Opus）来统一思想、引导方向，利用多个拥有强大记忆和执行能力的专家（Gemini）来处理细节，并通过人类监督（你）来保证信息质量，从而实现对复杂问题高效、聚焦、且能自我优化的探索。

## MapReduce
大多数智能体系统（agentic systems）都遵循MapReduce或动态规划（Dynamic Programming）的模式。

当模型生成输出时，能够判断它是否意图继续生成（内容），这一点很有用。

但问题在于，如果要求模型在输出末尾添加一个特定的token（词元）来标记“待续”状态，会显著缩短输出内容的长度——并且这个现象在所有模型上都普遍存在。
这意味着我需要手动阅读输出内容，要求（模型）生成更多，并检查确认内容的扩充不是为了扩充而扩充的无意义填充。

我们得到的其实是一个质量非常高的中间产物，可以用它来生成最终报告。如果我们前期的工作做得好，那么现在我们只需要在不丢失任何信息的前提下，重写这份内容即可。

在开始重写之前，我们可以使用 Claude Code 来清理和组织报告，并定期检查 `git diffs`（版本差异），以确保我们没有误删任何内容。

> 💡 这是一个非常有用的模式。尽管会消耗上下文（context）长度，但让智能体能够使用 diff（差异比较）来检查自身行为造成的影响，有助于让它们在执行任务时保持正轨，并在测试阶段改进其工具调用（tool calls）。

> 鉴于模型的这种本质特性，以下这个模式无论对于向智能体（agent）发出提示的人类还是AI，都同样有效：

1. 编写一个提示。
    
2. 运行它。
    
3. 在中途停止输出（或者让它完成）。
    
4. 调整最初的提示。
    
5. 重复以上步骤。
    

确保智能体在执行的初始阶段就走对方向，这一点至关重要——否则，最初的错误会一直影响后续的结果。如今大多数智能体系统试图通过多轮对话消息来进行纠错——但这代价是消耗了上下文长度（context length），并可能导致“上下文污染”（context poisoning）。最好能从一开始就避免出现那种，需要在任务进行到一半时告诉模型“不要去想大象”的窘境。

### **上下文管理 (Context management)**

在智能体（agentic）应用场景中，最重要的事情就是上下文管理。Claude Code 在这方面做得相当不错，但仍有一些显而易见的改进点可以着手。

首先，（单纯的）摘要总结是行不通的。任何用过 Cursor 或 Claude Code 的人都会告诉你，上下文摘要功能常常是导致整个流程出岔子的地方。

当尝试压缩上下文时，你真正想要实现的目标是：

- 保留有用的信息片段，同时剔除（有时是完全剔除）不必要的循环和无关内容。
    
- 维持用户或上级智能体（superagent）的偏好，无论多么细微。这些偏好有时会体现在回应的措cii辞中（例如`‘DON’T DO THAT’`和`‘ah - not like that’`这两种说法的区别）。
    
- 移除上下文中的重复内容。大多数长期运行的智能体上下文中都会有重复的信息片段——而这些信息往往是无用的。
    
- 重申当前的目标，以及围绕该目标的更宏观的背景。
    

在多轮对话中，最有价值的是那条由人类/上级智能体与子智能体（subagent）互动而逐渐形成的引导路径。当你仅仅进行摘要时，所有这些价值都会丢失，尤其是当执行摘要的是另一个不了解前因后果的智能体时。

以下是一些替代方案：

1. 在上下文耗尽前，当前智能体可以启动一个新的子智能体，并为其提供一个详尽的初始提示。有时你会发现这种方法的效果远胜于摘要。
    
2. 智能体可以自行识别并编辑上下文，以移除不重要的部分。

### 1. 孤立执行阶段 (The "Map" Step)

- **输入**: 每个Agent（1, 2, 3, 4）只接收两样东西：
    
    1. **它自己负责的那一块独立的数据 (Chunk)**。

- **过程**: Agent们就像在不同考场里做同一份试卷的学生。Agent 2不知道Agent 1写了什么，Agent 3也不知道Agent 2的进度。它们各自埋头分析自己拿到的那部分代码，并生成一份独立的分析报告（`Questions & Answers`）。
    
- **输出**: 产出4份完全独立的分析报告。
    

**结论：在这个阶段，它们之间没有任何信息交换。没有将Agent 1的总结过滤后作为额外上下文给Agent 2的操作。**

### 2. 交互与综合阶段 (The "Reduce" Step)

交互只发生在**第一阶段完全结束之后**，也就是在“Orchestration”（编排）阶段。

- **输入**: 编排器（无论是您本人，还是Opus 4）接收**所有4份独立的分析报告**。
    
- **过程**: 到这时，信息才第一次被汇总。编排器阅读所有报告，进行对比、清理、去重和提炼，形成一个对全局的、更完整的认知。
    
- **输出**:
    
    - 一份综合性的初步报告（`Synthesis`阶段的产物）。
        
    - 一套为下一轮分析设计的、全新的指令。

> 
> **译文**：“智能体似乎有能力处理这个...但它们很快就退化为**询问不存在的东西**，或者提出一些**其他智能体都无法回答的引导性问题**。我们的**上下文也快用完了**。”

**失败原因总结：**

1. **上下文污染**: Agent们被其他Agent的中间结果搞糊涂了，开始产生幻觉。

3. **上下文爆炸**: 频繁的交互迅速耗尽了宝贵的上下文空间。
