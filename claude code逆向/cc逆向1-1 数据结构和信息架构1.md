在之前的 apiMessage 接口中，我们看到 content 字段的类型是 string | ContentBlock[]。这里的 ContentBlock 就定义了那个数组中可以存放的“内容块”的种类。这表明系统中的消息不仅仅是纯文本，而是可以由多种不同类型的内容组合而成的富文本或多模态消息。

各个内容块 (Block) 的作用解析:

TextBlock: 文本块。最基础的类型，用于存放一段纯文本。
    
ImageBlock: 图片块。用于在消息中嵌入或引用一张图片。
    
ToolUseBlock: 工具使用块。这个非常关键，它代表 LLM 请求调用一个工具。这个块里会包含需要调用的工具名称 (tool_name) 和调用时需要传入的参数 (input)。这对应了我们之前状态图中的 ToolUseBlock 状态。
    
ToolResultBlock: 工具结果块。这是 ToolUseBlock 的配对块，用于将工具执行后的结果返回给 LLM。这个块里会包含被调用的工具的 ID 和执行的输出结果。这对应了状态图中的 ToolResultBlock 状态。
    
ThinkingBlock: 思考块。这是一种用于改善用户体验的块。当 LLM 需要较长时间来处理一个复杂请求时，它可以先发送一个 ThinkingBlock，让前端界面显示一个“正在思考中...”的动画或提示，告诉用户系统正在工作。
    
DocumentBlock: 文档块。用于引用或嵌入一个文档（如 PDF, DOCX）。注释 Platform-specific 指出这可能是特定平台才支持的自定义类型。
    
VideoBlock: 视频块。用于引用或嵌入一个视频。同样是平台特定的。
    
GuardContentBlock: 守卫内容块。这个名字暗示它与安全或验证有关。它可能是一种“护栏 (Guardrail)”机制，用于标记或过滤掉不安全、不合规的输入或输出，或者在执行敏感操作前请求用户确认。
    
ReasoningBlock: 推理块。这是一种元数据块，可能用于展示 LLM 的思考过程或推理链 (Chain of Thought)。将推理过程显式地作为一个内容块，可以用于调试、分析或向用户展示 AI 是如何得出结论的。
    
CachePointBlock: 缓存点块。这暗示了系统中有缓存机制。这个块可能用于指示某个结果是从缓存中获取的，或者指示这个块之后的内容可以被安全地缓存起来，以提高后续请求的响应速度。

这个接口本身不参与程序的运行时逻辑，它更像是一个静态的元数据或文档。它的作用是为开发人员提供关于不同 ContentBlock 类型的性能特征分析。这种分析对于系统优化、瓶颈排查和技术选型至关重要。

它使用了大O表示法 (Big O notation) 来描述算法的复杂性。

对 TextBlock, ImageBlock, ToolUseBlock 的性能分析:

TextBlock (文本块):
    
    memorySize: "O(text.length)": 内存占用与文本的长度成线性关系。文本越长，占内存越多。
        
    parseTime: "O(1)": 解析时间是常数时间。识别一个数据块是文本块这个动作本身非常快，与文本多长无关。
        
    serializeTime: "O(n)": 序列化（例如转换成 JSON 字符串）的时间与文本长度 n 成线性关系，因为需要处理每一个字符。
        
    streamable: true: 可流式处理。文本内容可以一个词一个词或一个字一个字地流式传输，非常适合打字机效果。
        
ImageBlock (图片块):
    
    memorySize: "O(1) + external": 内存占用很特别。对象本身（可能只存一个 URL 或引用）只占常数大小的内存 (O(1))。但它指向的外部资源（如 Base64 编码的图片数据或云存储 S3 上的文件）可能非常大。
        
    parseTime: "O(1)": 解析时间是常数时间。
        
    serializeTime: "O(size)" | "O(1) for S3": 序列化时间取决于实现方式。如果图片数据（如 Base64）直接嵌入消息体，时间与图片大小 size 成正比；如果只是引用一个 S3 链接，则时间是常数。
        
    streamable: false: 不可流式处理。通常图片作为一个整体来传输，不适合像文本那样进行流式处理。
        
ToolUseBlock (工具使用块):
    
    memorySize: "O(JSON.stringify(input).length)": 内存占用与工具输入的参数在转换成 JSON 字符串后的长度成线性关系。
        
    parseTime: "O(n) for JSON parse": 解析时间与 JSON 字符串的长度 n 成线性关系，因为需要完整解析整个 JSON 才能验证其有效性。
        
    serializeTime: "O(n)": 序列化时间也与 JSON 数据的大小成线性关系。
        
    streamable: true: 可流式处理。注释中明确指出，包含工具参数的 JSON 字符串本身可以像普通文本一样进行流式传输。这完美解释了上一个接口中 streamAccumulator.buffers 的用途——就是为了拼接这些流式传输过来的 JSON 片段。

// Inferred implementation of streaming JSON parser
class StreamingToolInputParser {
  private buffer: string = '';
  private depth: number = 0;
  private inString: boolean = false;
  private escape: boolean = false;

  addChunk(chunk: string): ParseResult {
    this.buffer += chunk;

    // Track JSON structure depth
    for (const char of chunk) {
      if (!this.inString) {
        if (char === '{' || char === '[') this.depth++;
        else if (char === '}' || char === ']') this.depth--;
      }

      // Track string boundaries
      if (char === '"' && !this.escape) {
        this.inString = !this.inString;
      }
      this.escape = (char === '\\\\' && !this.escape);
    }

    // Attempt parse at depth 0
    if (this.depth === 0 && this.buffer.length > 0) {
      try {
        return { complete: true, value: JSON.parse(this.buffer) };
      } catch (e) {
        // Try auto-closing unclosed strings
        if (this.inString) {
          try {
            return {
              complete: true,
              value: JSON.parse(this.buffer + '"'),
              repaired: true
            };
          } catch {}
        }
        return { complete: false, error: e };
      }
    }

    return { complete: false };
  }
}

这个类的目的是解决一个在与流式大语言模型（LLM）API 交互时非常常见且棘手的问题：如何处理分块传输（streamed）的 JSON 数据。

在之前的讨论中我们知道，当 LLM 决定使用工具时，它会生成一个 ToolUseBlock，其参数是一个 JSON 对象。为了提升实时性，LLM 会将这个 JSON 对象作为一个字符串，一小块一小块地（in chunks）发送过来。

标准的 JSON.parse() 函数必须在接收到完整且格式正确的 JSON 字符串后才能工作。如果你给它一个不完整的片段，比如 {"key": "va，它会立即抛出错误。

因此，StreamingToolInputParser 的作用就是作为一个状态机，接收这些零散的字符串片段，将它们拼接起来，并智能地判断何时拼接成了一个完整的 JSON 对象，然后才尝试进行最终的解析。是的，这个项目确实有一个机制来处理来自语言模型（LLM）的原始流式数据，并从中解析出工具调用（Tool Calls）。

不过，它可能不是一个独立的、被命名为“复杂的流式解析器”的模块，而是深度集成在 Task 类的核心逻辑中，特别是处理 LLM 响应的流式处理部分。

这个过程的核心在于 Task 类如何处理 assistant 角色的消息流。

工作流程解析：

发起 API 请求:
    
    recursivelyMakeClineRequests 方法会调用 attemptApiRequest，向 LLM 发起请求。
接收原始碎片流 (Raw Chunk Stream):
    
    LLM 以流式方式返回响应。这些响应是一些小的文本片段（chunks），比如 {"type": "text_delta", "text": "<exec"}，然后是 {"type": "text_delta", "text": "ute_com"} 等等。
实时处理和拼接:
    
    在 recursivelyMakeClineRequests 方法内部，有一个 for await...of 循环，它会遍历从 attemptApiRequest 返回的异步生成器（ApiStream）。
    presentAssistantMessage 方法被调用来处理每一个数据块。这个方法是关键，它负责将这些零散的文本块拼接成连贯的助理消息内容（assistantMessageContent）。
解析工具调用:
    
    当 presentAssistantMessage 方法将流拼接成完整的助理回复后，recursivelyMakeClineRequests 方法会继续执行。
    它会检查拼接好的助理回复中是否包含XML标签格式的工具调用，例如 <execute_command>...</execute_command> 或 <write_to_file>...</write_to_file>。
    项目中使用正则表达式来匹配和提取这些工具调用块及其参数。这个解析过程发生在 extractToolContent 之类的方法中（虽然这个方法在您当前可见的代码中是折叠的，但它是这个逻辑的一部分）。
准备并执行工具:
    
    一旦成功从流中解析出一个完整的工具调用，Task 类就会调用相应的工具执行方法，比如 executeCommandTool 或 writeToFile。
    工具执行的结果会作为新的上下文，再次发送给 LLM，形成一个完整的 "Reason-Act" 循环。

一个典型的工作流程如下：

连接: 核心CLI Agent（作为MCP客户端）启动，并连接到一个长期运行的、拥有数据库访问权限的后台服务（MCP服务器）。

握手 (能力协商): 后台服务向CLI Agent发送其 McpCapabilities，其中包含 tools: true。

发现 (工具发现): CLI Agent得知对方能提供工具，于是发送一个McpRequest：{ "method": "tools/list" }。

注册: 后台服务返回一个McpResponse，其 result 中包含一个 McpToolSpec 对象数组，其中一个描述了 query_database 工具。

代理: CLI Agent在自己的内存中动态创建一个“代理”工具。这个代理工具的 ToolDefinition 与其他本地工具类似，但其 call 函数的实现不是执行数据库查询，而是发起一个新的MCP请求：{ "method": "tools/execute", "params": { "name": "query_database", ... } }。

执行: 后台服务接收到执行请求，调用自己本地的、真正的工具实现，并将结果通过 McpResponse 返回。

完成: CLI Agent收到响应，完成这次远程工具调用。
