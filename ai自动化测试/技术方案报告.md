# 技术方案报告

## 目标

基于 `ai自动化测试` 文件夹内的全部材料，提出一个能落地的 AI 自动化测试技术方案，满足以下约束：

- 支持自然语言描述测试目标。
- 支持像脚本一样读取文件自动执行。
- 过程可见，不是纯黑盒。
- 能输出可协作的问题报告。
- 先以本地单机为主，再考虑后续扩展。

## 从材料中提炼出的硬性要求

### 来自 `需求.md`

- 自然语言控制功能操作。
- 自动验证结果。
- 文件化执行。

### 来自 `3.11会议纪要.md`

- 不能只给最终结果，要能看到过程。
- 重点是发现问题，而不是简单通过。
- 传统 Playwright 脚本维护成本太高。
- 需要面向桌面 / 多软件协同的扩展空间。

### 来自 `3.18会议纪要.md`

- 要一键脚本化，降低安装和运行门槛。
- 已有固定场景，后续必须降低新场景接入成本。
- 截图反馈给 AI 决策是现有方案的重要特征。
- 报告能力必须保留并增强。

### 来自 `前端 AI 自动化测试：brower-use 调研.md`

- `browser-use` 适合作为自然语言浏览器执行能力参考。
- `vibetest-use`、`web-eval-agent` 说明 MCP / IDE 是重要扩展方向。
- `qa-use` 说明平台化能力可以后置补齐。
- 成本与模型效果需要平衡。

### 来自 `小龙虾总结.md`

- 推荐的核心闭环是：目标 -> 执行 -> 观察 -> 判断 -> 纠错 -> 输出。
- 关键技术增量是视觉断言、环境自愈、动态规划和报告整合。

## 推荐总方案

建议采用：

**文件化场景 + 最小确定性执行器 + AI 规划与回退 + 统一报告系统**

换句话说，这不是纯脚本方案，也不是纯 Agent 黑盒方案，而是一个混合架构。

## 总体架构

### 1. 场景层

负责描述“要测什么”。

建议资产形态：

- Markdown 场景文件。
- YAML / JSON 场景文件。
- 内含目标、步骤、断言、环境要求和输出要求。

为什么要单独一层：

- 满足“像脚本一样读取文件自动执行”。
- 让场景可 review、可版本化、可复用。
- 降低对 prompt 临时发挥的依赖。

### 2. 规划层

负责把场景转成执行计划。

建议由 LLM 完成的部分：

- 解析自然语言目标。
- 拆解执行步骤。
- 把模糊描述转成结构化子任务。
- 在执行失败后调整下一步计划。

这里的核心不是“让模型写完整脚本”，而是让模型做任务编排与异常回退。

### 3. 执行层

负责稳定执行基础动作。

建议采用最小执行器思路，先封装高频稳定能力：

- 打开页面。
- 点击。
- 输入。
- 等待元素出现 / 页面加载。
- 切换标签页。
- 截图。
- 获取控制台日志。
- 获取网络请求摘要。
- 文件上传下载。

底层推荐：

- 浏览器操作以 Playwright 为稳定底座。
- AI 调度接口可以兼容 MCP / browser-use 风格能力。

原因是：

- Playwright 够稳。
- 团队已有相关认知。
- 可保留结构化控制能力。
- 方便后续做 trace、视频、日志采集。

### 4. 感知层

负责让系统不仅“操作”，还能“观察”。

建议包含：

- 页面截图。
- DOM 摘要。
- 元素文本。
- 控制台错误。
- 网络请求结果。
- 视觉 OCR。

这层是 AI 能做视觉判断、模糊匹配和问题发现的基础。

### 5. 智能回退层

负责在执行失败时不立即中断。

可交给 AI 的回退动作包括：

- 元素未找到时改用视觉定位或文本定位。
- 断言失败时补充截图与环境信息。
- OCR 失败时切换多模态识别。
- 页面跳转异常时尝试重新导航或回退。

但必须设置边界：

- 最大重试次数。
- 最大 token 消耗。
- 允许的工具列表。
- 是否允许修改本地环境。

### 6. 报告层

负责把执行结果变成可信交付。

建议输出两种报告：

- 结构化报告：JSON。
- 面向阅读的报告：Markdown / HTML。

核心字段至少包括：

- 场景名称。
- 执行时间。
- 每一步的动作、预期、实际。
- 截图和证据链接。
- 失败原因。
- 问题分类。
- 最终结论。

## 推荐执行模式

建议系统支持 3 种模式，而不是一种模式打天下。

### 模式 1：确定性模式

特点：

- 只执行结构化步骤。
- 不调用 AI 做大范围重规划。
- 适合高频稳定回归场景。

适合：

- 登录。
- 创建仓库。
- 表单提交。
- 基础 CRUD。

### 模式 2：AI 辅助模式

特点：

- 基础动作由执行器完成。
- 视觉判断、模糊对象匹配和失败分析交给 AI。
- 适合页面变化较频繁但仍有主流程约束的场景。

适合：

- 页面结构常改。
- 需要视觉校验。
- 需要更丰富的错误描述。

### 模式 3：AI 探索模式

特点：

- 由 AI 根据目标自主探索。
- 成本和波动最大。
- 更适合问题发现而不是稳定回归。

适合：

- 新页面初测。
- 探索式测试。
- 快速验证未沉淀为正式场景的功能。

## 推荐场景文件格式

建议采用“结构化头部 + 自然语言步骤”的混合格式。这样既便于程序读取，也能让人直接编辑。

示例：

```yaml
name: 登录并创建仓库
mode: ai_assisted
target: http://localhost:3000
preconditions:
  - 已启动本地服务
  - 使用测试账号
steps:
  - action: open
    value: /
  - action: login
    value:
      username: test_user
      password: secret
  - action: click_text
    value: 新建仓库
  - action: fill_form
    value:
      repo_name: ai-test-demo
assertions:
  - type: text_visible
    value: 仓库创建成功
  - type: screenshot_contains
    value: ai-test-demo
outputs:
  - markdown_report
  - json_report
  - screenshots
```

这样做的好处是：

- 简单场景可直接结构化执行。
- 复杂断言仍可交给 AI 补充解释。
- 便于后续做模板库。

## 推荐技术栈

### 本地 Runner

- Node.js / TypeScript
- CLI 入口
- 一键安装脚本
- 环境检查脚本

理由：

- 团队当前语境更接近前端和脚本体系。
- 本地安装、日志采集和 Playwright 集成更顺手。

### 浏览器执行器

- Playwright

理由：

- 稳定。
- 工具链成熟。
- 支持截图、trace、视频、网络、控制台采集。

### AI 接入层

- 统一 LLM 接口抽象
- 支持云模型和本地模型切换
- 记录 token 消耗

理由：

- 方便后续做成本控制。
- 降低模型供应商绑定。

### AI Agent 适配层

- 可兼容 `browser-use` 风格任务编排
- 预留 MCP Server / Client 入口

理由：

- 便于后续接 Claude / Cursor / IDE。
- 不必现在就深绑定某一个上层产品。

### 报告存储

- 本地文件夹输出
- Markdown / HTML
- JSON 原始数据
- 截图与 trace 同目录

理由：

- 便于当前阶段最小闭环。
- 无需先做数据库和平台。

## 推荐工程目录

可以按如下思路组织：

```text
ai-test-runner/
  scenarios/
  prompts/
  skills/
  runner/
  adapters/
  reports/
  scripts/
```

建议职责：

- `scenarios/`：场景文件
- `prompts/`：AI 规划、报告、问题归类 prompt
- `skills/`：高频动作封装
- `runner/`：主执行逻辑
- `adapters/`：Playwright、LLM、MCP、browser-use 适配
- `reports/`：运行输出
- `scripts/`：安装、自检、一键运行

## 为什么推荐“最小执行器 + AI 回退”

这个组合同时解决了当前材料里最突出的矛盾。

### 解决脚本维护问题

通过最小执行器把稳定动作抽出来，避免每个场景都堆一堆低层 Playwright 代码。

### 解决纯 AI 不可控问题

让 AI 主要负责规划、视觉判断和回退，而不是让它从头到尾完全自由发挥。

### 解决场景复用问题

场景文件可以作为团队共享资产，而不是每次重新写 prompt。

### 解决过程可信问题

执行器天生能采集步骤、日志、截图和 trace，报告更容易建立信任。

## 阶段实施建议

### 第 1 阶段：本地最小闭环

目标：

- 一键安装。
- 一键执行。
- 6 个固定场景稳定跑通。
- 输出 Markdown 报告和截图。

此阶段不追求：

- 平台化。
- K8S。
- 多租户。
- 大规模调度。

### 第 2 阶段：AI 辅助增强

目标：

- 接入视觉断言。
- 接入失败后的局部重试。
- 支持自然语言补充断言。
- 增强问题分类和报告质量。

### 第 3 阶段：IDE / MCP 集成

目标：

- 从本地命令行延伸到 IDE。
- 支持开发过程中即时触发。
- 把测试结果直接反馈到开发流。

### 第 4 阶段：轻平台化

目标：

- 场景管理。
- 执行历史。
- 定时任务。
- 通知与检索。

前提：

- 底层场景和执行能力已稳定。

## 风险与应对

### 风险 1：模型成本过高

应对：

- 默认优先走确定性步骤。
- 只在失败和视觉判断阶段调用 AI。
- 记录单场景 token 消耗。

### 风险 2：AI 回退过多导致结果不稳定

应对：

- 设置最大回退次数。
- 对每次回退记录理由。
- 关键场景允许禁用 AI 回退。

### 风险 3：新场景仍然难加

应对：

- 把高频动作收敛成 skill。
- 提供场景模板。
- 把“添加一个新场景”作为第一优先级体验指标。

### 风险 4：执行过程不透明

应对：

- 默认保存截图。
- 记录每一步动作、输入和断言。
- 保存 trace 与控制台日志。

## 最终建议

如果只给一句技术结论：

**当前最适合的技术方案，是以 Playwright 为稳定执行底座，以场景文件为资产，以 AI 作为规划、视觉理解和异常回退层，先做本地一键闭环，再逐步延伸到 MCP / IDE 和轻平台能力。**

这条路线最符合当前目录里的全部材料，也最有机会在“可用、可信、可扩展”之间取得平衡。
